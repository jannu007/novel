# 小説を書くアプリと、読むアプリ

このリポジトリには、**独立した4つのアプリ**が入っています。どれも完全無料・
サーバー不要で、ブラウザから**そのままインストール**して使えます（APKもストア登録も不要）。
書くほうは Amazon KDP（Kindleダイレクト・パブリッシング）で販売できる原稿
（EPUB / DOCX / 印刷用PDF）を作成でき、読むほうは手元の Markdown を
販売されている電子書籍と同じ体裁で読めます。

| アプリ | URL | 特徴 |
| --- | --- | --- |
| **製本所（せいほんじょ）** | `/md/` | 書き上がった**Markdownを貼る（読み込ませる）だけ**で、章・目次・リンクが自動で組まれ、内容に合った表紙と挿絵まで付いた本になります。KDPに出せるEPUB・Word・PDFを書き出せます。 |
| **栞（しおり）** | `/read/` | 手元の `.md` を、Amazonで買った本のように縦書き・ページめくりで読むリーダー。**左から右へスワイプ**でページが進みます。 |
| **語り部（かたりべ）** | `/voice/` | 手元の `.md` を**朗読**します。読み上げの声は**端末の中だけで話すもの**しか使わないため、本文がメーカーのサーバーへ渡りません。 |
| **文机（ふづくえ）** | `/desk/` | スマートフォンでの執筆を中心に、画面下のタブと和紙・墨の配色で作り直した執筆アプリ。 |
| **小説執筆スタジオ** | `/` | 起承転結の自動下書きや表紙・挿し絵の自動生成まで含んだ従来の執筆アプリ。 |

5つは**別々のデータベース**に保存するため、同じブラウザで併用しても作品や蔵書が混ざりません。
その代わり、**小説執筆スタジオで書いた作品は文机の一覧には出てきません**。同じブラウザなら、
文机があちらの作品を見つけて「小説執筆スタジオにN件の作品があります」と案内するので、
そこからひと押しで取り込めます（あちらの作品はそのまま残ります）。別の端末へ移すときは、
片方でバックアップを保存し、もう片方で読み込んでください。
ルビ記法の解析や校正エンジン・書き出し処理（`src/lib`）は共通の実装を使っています。

## インストールして使う（PWA）

どのアプリも[インストール可能なPWA](https://web.dev/progressive-web-apps/)として
**別々にインストールできます**。使いたいアプリのURLをブラウザで開いて、以下の操作をしてください。

- **デスクトップ（Chrome / Edge）**：アドレスバーのインストールアイコンをクリック
  （小説執筆スタジオは画面右上の「📲 インストール」ボタンからも可能）。
- **Android（Chrome）**：メニュー（⋮）→「アプリをインストール」。
- **iOS（Safari）**：共有ボタン →「ホーム画面に追加」。

インストール後は独立したウィンドウ（アイコン付き）で起動し、一度読み込んでおけば
オフラインでも執筆・読書を続けられます（Service Workerによるオフラインキャッシュ）。
4つはスコープが別なので、それぞれ別のアプリとしてホーム画面に置けます。

## 製本所（せいほんじょ）— Markdownを売れる本にする

**すでに書き上がっている原稿を、売れる本のかたちに変えるためのアプリです。**
Markdownを貼るか、ファイルを落とすだけで、あとは自動で進みます。

### したことは、貼るだけ

- **貼った瞬間に本になります。** 入力欄に貼る、ファイルを落とす、どちらでも構いません。
  `01-序章.md` `02-第一章.md` のように**複数ファイルをまとめて渡す**と、ファイル名の順に
  つないで1冊にします。画像ファイルも一緒に落とせば、本文の `![](ファイル名)` が
  そのまま挿絵になります。
- **章と目次が自動で組まれます。** 見出しの使い方（`#` と `##` のどちらが章の粒度か）を
  原稿から判定して章に切り分け、EPUBの目次（nav.xhtml・toc.ncx）、読者に見える目次ページ、
  Wordの見出しスタイルを同時に作ります。判定が思ったとおりでなければ、画面で切り替えられます。
- **見出しの無い原稿でも章に分かれます。** 「第一章」「プロローグ」のような行や、
  水平線（`---`）を手がかりにします。
- **リンクがつながります。** `[第三章](#第三章)` のような原稿内のリンクは、
  章をまたいだ**本の中のリンク**として解決します（記号や大文字小文字の違いは吸収します）。
  行き先が見つからないものは、文字だけを残して知らせます。
- **脚注 `[^1]`** は、Kindleでタップすると開くポップアップ注（`epub:type="footnote"`）になります。
- **ルビ `｜漢字《かんじ》`・傍点 `《《ここ》》`** は、EPUBでは `<ruby>` と圏点、
  Wordでは**Wordのルビ機能そのもの**（`w:ruby`）として書き出します。
- 箇条書き・引用・表・コード・強調・打ち消し・参照リンク・自動リンク・
  YAMLフロントマター（`title:` `author:` など）にも対応しています。

### 内容に合った表紙と挿絵が、そのまま付いてきます

本文をそのまま読み取って、**情景・時刻・季節・天候・気分・ジャンル**を見立て、
その情景をCanvasで描き起こします。海辺の夜、雪の街、夕暮れの城、宇宙、教室――
原稿が変われば絵も変わります。

- **表紙**は 1600 × 2560ピクセル（KDP推奨の 1 : 1.6）。縦書きの題字を組み、
  「別の絵にする」「文字の配置を変える」で選び直せます。自分の表紙に差し替えることもできます。
- **章の扉絵**は、その章の本文から見立てた情景で1枚ずつ描きます。
- **画像生成AIも素材サイトも使いません。** 通信は一切発生せず、費用もかからず、
  生成物の権利関係も濁りません。同じ原稿からは毎回まったく同じ絵ができます。

### そのままAmazonへ

- **EPUB**（Kindle電子書籍）… 縦書き・右綴じ／横書きを選べます。表紙・扉絵・目次・
  内部リンク・脚注を含み、KDPにそのまま登録できます。
- **Word（DOCX）**… ペーパーバック用。判型（5×8 / 5.5×8.5 / 6×9インチ、A5、B6、A4）と
  ノドの余白をKDPの規定に合わせ、縦書き（`tbRl`）、見出し、ルビ、脚注、本物のハイパーリンクを
  そのまま持ち込めます。
- **印刷・PDF**… ブラウザの「PDFとして保存」で配布用のPDFになります。
- **表紙画像**（JPEG）・**テキスト**も単体で書き出せます。
- **出す前の確かめ**として、題名・著者名・章立て・文字数・表紙の縦横比・外部リンクなどを
  KDPの観点で点検し、登録手順も画面に載せています。

### 原稿を外に出さない

- **通信そのものを禁止しています。** HTMLに `connect-src 'none'` を含む厳しいCSPを
  書き込んでいます。何かが原稿を送ろうとしても、ブラウザが通信を止めます（画面の「安全性」で、
  外部から読み込んだファイル数が0であることを実際に数えて表示します）。
- **既定では何も保存しません。** 原稿はメモリの中だけにあり、タブを閉じれば消えます。
  「この端末に保存する」を選んだときだけ、その端末のIndexedDBに保存します。
- **原稿の中のHTMLを実行しません。** Markdownの解析器が生HTMLを文字として扱い、
  `<script>` などは中身ごと捨てます。表示にも `dangerouslySetInnerHTML` を使っていません。
- **危ないリンクを本に入れません。** `javascript:` のようなURLは取り込みの段階で文字だけにし、
  書き出したEPUB・Wordにも残しません。
- **Markdownの解析も自前**（`src/md/markdown.ts`）です。外部のMarkdownライブラリを足さないことで、
  未発表原稿を扱ううえでの供給網（サプライチェーン）の危険を減らしています。
- アカウントも料金も広告も、行動を記録する仕組みもありません。オフラインでも動きます。

## 栞（しおり）— Markdownを本のように読む

手元の Markdown ファイル（`.md` / `.txt`）を本棚に入れて、**書店で買った電子書籍と
同じ体裁**で読むためのアプリです。アカウント登録も課金もなく、通信も一切行いません。

### 読み方

- **左から右へスワイプすると次のページ**に進みます（縦書きの本と同じ向き）。
  右から左へなぞれば前のページに戻ります。指の動きにページが付いてきて、
  離した瞬間にめくれるか戻るかが決まります。すばやく払うだけでも送れます。
- 画面の**左寄りをタップで次のページ**、**右寄りで前のページ**、**中央をタップ**すると
  上下の操作パネルが隠れ、本文だけになります。
- パソコンでは **← →・スペース・PageUp/PageDown・Home/End** でも操作できます。
  横書きに切り替えたときは、洋書と同じで左右の向きが入れ替わります。

### インストールして使う

本棚の「アプリとして入れる」から、お使いの端末での入れ方を確認できます。
インストールできるブラウザ（Android版Chrome・デスクトップのChrome/Edgeなど）では、
上部に「インストール」ボタンが出て、その場で入れられます。iPhone・iPadでは
Safariの共有ボタンから「ホーム画面に追加」を選んでください。

入れておくと、アドレスバーのない全画面のアプリとして開き、電波がなくても本棚を開けます。
端末のファイル一覧で `.md` を選んだときの「アプリで開く」や、ファイルアプリの
「共有」の宛先にも並びます（対応ブラウザのみ）。

#### 新しい版が必ず届くようにする

オフライン用の保存が古い版を抱えたままだと、**直したはずの不具合がいつまでも
直らないように見えます**。実際にそうなったため、次の3つを入れています。

- **サービスワーカーの登録を、起動処理のいちばん先に行います**（`src/read/main.tsx`）。
  以前は最後に置いていたので、手前の処理がその端末でたまたま失敗すると登録まで届かず、
  ブラウザがこれをアプリと見なさなくなって**インストールできなくなる**恐れがありました。
  登録は画面の表示に何も依存しないので、先に済ませます。あわせて、二重の備えである
  通信の遮断や配色の初期化は、失敗しても画面が開くようにしてあります。
- **新しい版を見つけたら、待たせずに交代させます**（`SKIP_WAITING`）。既定では新しい
  サービスワーカーは「待機」のまま残り、その場の画面をすべて閉じるまで交代しません。
  スマートフォンではアプリを完全に終了することが少ないため、待たせると何日も
  古い版のままになります。
- **画面（`index.html`）はブラウザの控えを飛ばして取り立てを使います**（`cache: 'reload'`）。
  配信元が「10分は控えを使ってよい」と言ってくるため、そのままだと新しい版を出しても
  古い画面が返り、そこから読み込むJavaScriptも古いままになります。

いま動いている版・サービスワーカーの状態・アプリとして起動しているかは、
本棚の「保存データ」の**アプリの状態**で確認できます。それでも古いままのときは、
同じ画面の「最新の版にする」で控えを捨てて取り直せます（本棚の中身は残ります）。

### 本のように読める組版

- **縦書き（右から左）が既定**です。組み上がった**1行1行の位置をブラウザから測って**
  ページに割るので、**行がページの境目で切れることがありません**。ルビのように行から
  はみ出して組まれるものも、行1本ぶんとしてまとめて扱います。
- 挿絵がページをまたぐとき、見出しがページの末尾に取り残されるときは、
  自動的に次のページの先頭へ送ります（書籍の組版と同じ配慮）。
- 見出しで章を分け、**目次**からどこへでも飛べます。長すぎる章は読みやすい大きさに
  自動で分割します。
- **字の大きさ・行の間・余白・書体（明朝／ゴシック）・配色（紙／古書／夜）・縦横**を
  変更でき、設定は次回にも引き継がれます。組み直したあとも**同じ場所から読み続けられます**。
- **読んでいた場所は自動で記録**され、本棚には進み具合が表示されます。
  **しおり**を挟んだり、本文を**検索**して見つけた場所へ飛ぶこともできます。
- ルビ（`｜漢字《かんじ》`）と傍点（`《《強調》》`）に対応しています。縦書きでは
  親文字の右に読みがつき、傍点は文字の上に打たれます。

### 文字数の数え方

「文字数」は数え方で1割ちかく変わります。同じ原稿でも、Markdownの記号（`#`・`｜`・`《》`）
を数えるか、ルビの読みを数えるか、空白と改行を数えるかで答えが違うためです。
どれか1つだけを黙って出すと「実際と合わない」ことになるので、**4通りをまとめて数え**、
本棚の「◯字・約◯分」を押すと内訳が出るようにしています（`src/read/count.ts`）。

| 数え方 | 内容 |
| --- | --- |
| **地の文** | 見出し（章題）・Markdownの記号・ルビの読み・空白・改行を数えません。**同じリポジトリの執筆アプリ（文机・小説執筆スタジオ・製本所）とまったく同じ数え方**で、`src/lib/textStats.ts` の `countChars` と一致することを確かめています。書いているときに見ていた数とそのまま突き合わせられます。**本棚に出しているのはこれ**で、読了時間もこの数から出します。 |
| ＋ 見出し | 地の文に、章題の文字を足したもの。 |
| ＋ ルビの読み | さらに `｜漢字《かんじ》` の「かんじ」を足したもの。 |
| 原文そのまま | 取り込んだファイルの長さ。文章を書く道具（エディタ）が出す数は、たいていこれに近くなります。 |

数える対象は地の文・引用・箇条書き・表・コードで、挿絵の代替文字は
読者に見えないので数えません。全角スペースによる字下げも空白として除きます。

文字数は取り込んだときに数えて保存するため、**数え方を直しただけでは本棚にある本は
古い数のまま**になります。そこで保存する記録に数え方の目印（`countRule`）を持たせ、
目印が古い本は次に本棚を開いたときに原文から数え直して保存し直します
（原文は必ず残してあるので、取り込み直す必要はありません）。数え直しは棚を出したあとに
行うので、長い本が何冊あっても棚が真っ白になりません。一度直せば目印が付き、次からは何もしません。

### 本の入れ方

- 「本を追加」から `.md` を選ぶ（複数まとめて選べます）
- 本棚の画面に**ファイルをドラッグ＆ドロップ**する
- 文章を**貼り付けて1冊にする**
- インストール済みなら、OSの「このアプリで開く」から `.md` を直接開く

- ファイルアプリで `.md` を選び、**共有 → 栞**（インストール済みのとき）

**ファイル選択は、Androidで確実に動く条件にそろえてあります。** 同じ端末で問題なく
動いていた別のアプリと突き合わせて分かった条件は、次の3つです。

- **種類（`accept`）を指定する。** 指定しないと、選択画面にファイルアプリが出てこず
  「カメラ」だけになる端末があります。
- **`multiple` を付けない。** 複数選択を求めると、それに対応しないファイルアプリが
  候補から外されます（Samsungの「マイファイル」など）。
- **`<label>` から開く。** 利用者が入力欄そのものを押した形にします。

それでも出ないときのために、「種類を指定せずに選ぶ」「まとめて選ぶ」を
本棚の「本の入れ方」に用意しています。取り込むときは拡張子ではなく
**中身が文字として読めるか**で判断するので、拡張子のないテキストも取り込めます
（画像やPDFはその場でお断りします）。

それでも端末の選択画面が使いにくいことがあるため、**共有からの受け取り**（Web Share
Target）にも対応しました。ファイルアプリから「共有 → 栞」を選ぶと、Service Worker が
受け取って本棚に追加します。本棚の「本の入れ方」に、この手順と、選択画面に
カメラしか出ないときのコツをまとめてあります。

**アプリ内ブラウザについて。** LINEやメールなどのアプリの中で開いた画面
（アプリ内ブラウザ）では、ファイル選択のしくみを**そのアプリ自身が用意している**ため、
候補が「カメラ」「写真」だけになることがあります。これはページ側からは変えられません。
そこで、その環境だと分かったときは本棚の上に知らせを出し、**Chromeで開き直す**ボタンと
**リンクをコピー**するボタン、そして選択画面を使わない入れ方（共有・貼り付け）を
案内しています。

なお、うまく選べなかったことを見つけて案内を出す仕組みは、ふだんの画面で
邪魔になるため設けていません。代わりの入れ方は「本の入れ方」にまとめてあります。

先頭に `---` で囲んだ**フロントマター**（`title:` `author:`）があれば書誌として使い、
無ければ最初の見出し、それも無ければファイル名を題名にします。文字コードは
UTF-8 のほか、**Shift_JIS・EUC-JP も自動判別**します。表紙は題名から自動生成され、
同じ本にはいつも同じ表紙がつきます。取り込んだ原文はそのまま保存しているので、
いつでも元の `.md` として取り出せます。

### 安全のしくみ

読む対象が「他人からもらったファイル」になりうるため、次の設計にしています。
方針は「**外へ出る経路を、実装ではなくブラウザの機能で塞ぐ**」です。実装で気をつける
だけだと、うっかり書き足された一行で破れます。塞いだうえで実装も守る、の二重にしています。

- **送る手段そのものを禁止しています。** 配信されるHTMLに
  [CSP](https://developer.mozilla.org/ja/docs/Web/HTTP/CSP) の `connect-src 'none'` を
  書き込んでいます。これは `fetch` / `XMLHttpRequest` / `WebSocket` / `sendBeacon` /
  `EventSource` を**すべて**止める指定で、仮に本文を送る処理が紛れ込んでも、その処理は
  ブラウザに拒否されて動きません。あわせて `default-src 'none'` を土台に、
  `img-src` は `self data: blob:`（＝端末の中のものだけ）、`media-src` / `object-src` /
  `frame-src` / `child-src` は `'none'`、`base-uri` と `form-action` も `'none'` にしています。
- **送る道具そのものを取り上げます。** 起動直後に `fetch` / `XMLHttpRequest` / `WebSocket` /
  `EventSource` / `RTCPeerConnection` / `navigator.sendBeacon` を、`writable: false` かつ
  `configurable: false` で置き換えます（`src/read/lockdown.ts`）。差し替えも `delete` もできません。
  CSPは「配信されたHTMLの宣言をブラウザが守る」前提なので、`<meta>` のCSPを読み飛ばす
  アプリ内ブラウザや、CSPの効かない拡張機能に対する備えです。とくに **WebRTC は
  `connect-src` の対象外になる環境がある**ため、ここで塞ぐ意味があります。
- **ブラウザの翻訳機能を止めます。** `<html translate="no">` と `<meta name="google"
  content="notranslate">` を入れています。ページ翻訳は**本文を翻訳サーバーへ送って**
  行われるうえ、ブラウザ自身の機能なので **CSPでは止まりません**。
- **入力欄のスペルチェックを切ります。** `spellCheck={false}` は見た目の指定ではなく安全の指定です。
  ブラウザの「高度なスペルチェック」は入力文字を**メーカーのサーバーへ送って**照合します。
  貼り付け欄には本1冊ぶんの原稿が入りうるので、検索欄・題名欄とあわせて対象から外しています。
- **本の題名を `document.title` に入れません。** タブ名は常に「栞」です。ここに入れた文字は
  閲覧履歴・タブ一覧・アプリ切り替え画面に残り、ブラウザの同期があれば他端末にも渡るためです。
- **本文をHTMLとして解釈しません。** Markdownの解析結果は文字列ではなく構造（AST）で返し、
  表示はReactの要素として組み立てます。本文からHTMLを作る処理（`dangerouslySetInnerHTML`）は
  このアプリに1か所もないため、`<script>` と書かれていても**ただの文字**として表示されます。
- **外部リンクは、押しただけでは開きません。** `javascript:` などの行き先は解析時に取り除き
  （通すのは `http` / `https` / `mailto` と本の中の見出しだけ）、残った外部リンクも
  `<a href>` にはせず、押すと行き先のURLを表示して確認を求めます。承諾したときだけ
  `noopener noreferrer` かつ参照元なしで開きます。誤タップで外に接続が飛ぶことはありません。
- **外部の画像を読み込みません。** 本に埋め込まれた画像（`data:`）だけを表示し、
  それ自体がスクリプトを持てる SVG は除外します。本文に追跡用の画像URLが書かれていても、
  解析の段階で捨てられ、さらにCSPでも読み込めません（読みに行くこと自体が発信になるため）。
- **表紙も端末の中で描いています。** 本文から配色と模様を決めてCanvasで描き起こすだけで、
  画像生成AIにも素材サイトにも本文を渡しません（`src/read/cover.ts`）。
- **他ページへの埋め込みを拒否します。** `window.top !== window.self` のときはアプリを
  起動しません（`frame-ancestors` は `<meta>` では効かず、GitHub Pages では応答ヘッダも
  足せないため、スクリプト側で止めています）。
- **解析に外部の部品を使いません。** Markdownの解釈は `src/read/markdown.ts` だけで完結しており、
  依存ライブラリ経由でコードが差し替えられる危険（サプライチェーン攻撃）を断っています。
- **保存はこの端末だけ。** 本はブラウザのIndexedDBにのみ保存され、まとめて削除もできます。
  取り込むファイルは拡張子と大きさ（16MBまで）を確かめてから、必ず「文字」として読み込みます。
- **確かめられるようにしています。** 本棚の「安全のしくみ」に、その画面を開いてからの
  外部通信の件数（`performance.getEntriesByType('resource')` を数えたもの）を出しています。
  機内モードのままで取り込みも読書もできるので、実際に切って確かめられます。
- **崩れたらビルドが失敗します。** `scripts/check-shiori-safety.mjs` が `npm run build` の
  一部として走り、**実際に配信される `dist/` の中身**に対して、CSPの必須指定・翻訳の禁止・
  `img-src` の内容・通信の道具の呼び出し・`dangerouslySetInnerHTML` の不在を確かめます。
  1つでも崩れていれば終了コード1でビルドを止めるので、公開されません。
  ここで文字列や注釈や正規表現を取り除いてから調べているのは、`/["']/` のような
  正規表現を文字列の始まりと読み違えると、以降がまるごと見逃されるためです
  （実際にその状態で本物の `fetch(` を素通ししたので、検査の側を直しました）。

#### アプリでは守れない範囲

正直に書きます。以下はアプリの外側なので、栞の実装では防げません。

- **利用者自身の操作。** 確認のうえで外部リンクを開いたとき、元の `.md` を自分で誰かに
  送ったときは、その分だけ外に出ます。
- **端末そのもの。** 画面の撮影、端末を他人に使われること、端末に入っている別のアプリからの
  のぞき見は、Webアプリの側では防げません。画面ロックの利用をおすすめします。
- **アプリ内ブラウザ。** LINEやメールのアプリの中で開いた画面は、そのアプリを通して
  表示されています。**ホーム画面に入れて**使うのが確実です。
- **配信元の記録。** 栞そのものを読み込むときだけは GitHub Pages に接続が残ります。
  そこに渡るのは「栞を開いた」という事実だけで、本の中身も題名も渡りません。
  インストール後はオフラインで起動するため、その接続も起きなくなります。

## 語り部（かたりべ）— 本の中身を外に出さない朗読アプリ

手元の Markdown ファイル（`.md` / `.txt`）を、**端末の中だけで朗読**するアプリです。
一文ずつ読み上げ、いま読んでいる文が画面で光ります。目で追ってもよく、画面を消して
耳だけで聴くこともできます。アカウント登録も課金もなく、通信も一切行いません。

### できること

- **一文ずつの朗読と追従表示。** 読んでいる文が光り、画面が自動で送られます。
  文をたたけば、そこから読み直します。
- **ふりがなをそのまま読ませられる。** `｜終電《しゅうでん》` と書くと、画面には
  「終電」を出したまま、声には「しゅうでん」を渡します。人名や地名も思ったとおりに読ませられます。
- **章ごとの移動と目次。** 章送り・一文送り・つまみでの移動、残り時間の目安。
- **おやすみタイマー。** 10〜60分で自動的に止まります。
- **速さ・高さ・音量・声の選択。** 声は端末に入っているものから選びます。
- **表とソースコードは既定で飛ばす。** 小説を聴くのに邪魔になるためで、設定で読ませられます。
- **オフライン。** 一度開けばインストールでき、電波が無くても動きます。

### 本の入れ方

- 上の「本を入れる」から `.md` / `.txt` を選ぶ
- 書棚の画面に**ファイルをドラッグ＆ドロップ**する
- ファイルアプリで `.md` を選び、**共有 → 語り部**（インストール済みのとき）
- インストール済みなら、OSの「このアプリで開く」から `.md` を直接開く

**ファイル選択は、Androidで確実に動く条件にそろえてあります。** 語り部だけ、選ぶ画面に
ファイルアプリが出てこず「カメラ」「写真と動画」しか並ばない、という報告がありました。
栞・製本所では起きていなかったので、入力欄の書き方を突き合わせて違いをなくしています。

- **種類（`accept`）を、よく知られたものだけ短く指定する。** 指定しない（あるいは
  見慣れない拡張子を混ぜる）と、端末が「なんでも」の求めとみなして、
  カメラと写真だけを出すことがあります。
- **`multiple` を付けない。** 複数選択を求めると、それに対応しないファイルアプリが
  候補から外されます（Samsungの「マイファイル」など）。
- **`<label>` から開く。** 利用者が入力欄そのものを押した形にします
  （JavaScriptから開くと、はじかれる端末があります）。
- **`hidden` で消さない。** 見えないだけの形（`.file-input`）にしておきます。
  消した入力欄をプログラムから押すと、候補が減ることがあります。

それでも出ないときのために、書棚の「ほかの入れ方」に、条件を変えた入力欄
（「種類を指定せずに選ぶ」「まとめて選ぶ」）と、**選ぶ画面を通らない入れ方**
（共有からの受け取り・「このアプリで開く」）をまとめてあります。
`file_handlers` は前から名乗っていたのに受け取り口が無かったので、
書棚で `launchQueue` を受け取るようにしました。

取り込むときは拡張子ではなく**中身が文字として読めるか**で判断するので、拡張子の無い
テキストも入ります（画像やPDFはその場でお断りします）。なお、LINEやメールなどの
**アプリ内ブラウザ**では選択のしくみを親アプリが用意しているため、候補がカメラと写真
だけになることがあります。これはページ側から変えられないので、その環境だと分かったら
書棚の上に知らせを出し、**Chromeで開き直す**ボタンと**リンクをコピー**するボタンを出します。

### 朗読アプリで本文が漏れるとしたら、通信ではなく「声」から

ここがこのアプリの中心です。読むだけのアプリなら、通信を全部塞げば本文は端末から出ません。
ところが**読み上げ**となると事情が変わります。ブラウザの音声合成に登録されている声には、
大きく2種類あるためです。

1. **端末の中で音を作る声**（`localService === true`）… OSに入っている読み上げエンジン。
   文字は端末の外に出ません。
2. **メーカーのサーバーで音を作る声**（`localService === false`）… 文字をネット越しに送り、
   返ってきた音を鳴らします。パソコン版Chromeの「Google 日本語」などがこれにあたります。

2 の声に本文を渡すと、**本文はそのままメーカーのサーバーへ送られます**。しかもこの送信は
ブラウザ自身が行うため、ページに掛けた CSP（`connect-src 'none'`）では止まりません。
`fetch` を取り上げる細工（`lockdown.ts`）も一切効きません。

語り部は、ここを次の決まりで守っています（`src/voice/speech.ts`）。

- 話す前に**必ず声を1つ選び**、`utterance.voice` に入れる。
- 選べるのは `localService === true` の声だけ。**一覧にも出しません。**
- 声を指定できなかったとき、端末の中で話す声が1つも無いときは、**読み上げません。**
  代わりに、なぜ読み上げないのかを画面に出します。

最後の1つが肝心なところです。`utterance.voice` を空のままにすると、ブラウザが既定の声を
勝手に選びます。その既定が 2 の声だと、黙って本文が送られてしまいます。
**「読めない」より「黙る」ほうを選びました。**

伏せた声の数は設定画面に出しています（「使わずに伏せた声：2個」のように）。
「通信しません」と書くだけなら誰でも書けるので、その端末で実際に何個を使い、
何個を伏せたのかを、その場で数えて見せています。

もう一つの備えとして、**一度に声へ渡すのは一文だけ**にしてあります。仮に将来この判定が
すり抜けても、渡っているのは常に一文であって、本一冊ではありません。

この2つは、ビルドのたびに機械が確かめます（`scripts/check-safety.mjs`）。
`speech.ts` から判定が減っていないか、`speech.ts` を通さずに声へ文字を渡す場所が
増えていないかを見て、崩れていればビルドを失敗させます。実際に判定を1か所消し、
別の画面から直接読み上げる行を足して、**どちらもビルドが止まることを確かめてあります**。

### ひとり版 — HTMLファイル1つだけにする

配信版（`/voice/`）はインストールすればオフラインで動きますが、それでも2つ残ります。

1. **配信元の記録。** 読み込むときだけ GitHub Pages に接続が残ります（渡るのは
   「開いた」という事実だけで、本の中身は渡りません）。
2. **同じ置き場の隣人。** 同じサイトに別のアプリが同居していると、それらは互いの
   保存領域を読める間柄になります。今はどれも通信しませんが、「通信しないアプリが
   隣にいる」ことに依存している状態ではあります。

**ひとり版**（`kataribe-standalone.html`）は、語り部ぜんぶを1つのHTMLファイルに
収めたものです。手元に保存して `file://` で開けば、この2つとも消えます。置き場が
無いので配信元が無く、隣人もいません（`file://` は1つ1つが別の生成元です）。
設定画面の「ひとり版を保存する」から落とせます。

- **CSPは緩めていません。** 1ファイルにするとJavaScriptがHTMLの中に入るので、
  素直にやると `script-src 'unsafe-inline'` が要ります。それでは元も子もないので、
  コードのハッシュ（sha256）を測ってCSPに書いています。**そのコードちょうど1つだけ**が
  許され、1文字でも書き換われば動きません（差し替えの細工が効かない）。
  実際に1行差し込んだファイルを作り、CSPに拒まれて起動しないことを確かめてあります。
- **書棚は残りません。** `file://` ではブラウザが IndexedDB を使わせないためで、
  開くたびにファイルを選び直します。裏を返せば**端末に何も残らない**ということで、
  端末を後から調べられても本の中身は出てきません。設定画面にその状態を出します。

作り方は `vite.standalone.config.ts` と `scripts/make-standalone.mjs`。
`npm run build` に含まれています。

### 検査を、同居しているアプリぜんぶに広げました

同じサイトに置かれたページは互いの保存領域を読めるので、**どれか1つでも外へ送れる口が
開いていれば、そこが語り部の蔵書の抜け道**になります。そこで検査を広げました。

- 執筆アプリ3つにも、CSPに `connect-src 'none'` があること、原文に通信の道具が
  無いことを確かめます。
- 栞と語り部については、**入口から読み込みの筋をたどって**、画面に実際に届く
  JavaScriptを1つ残らず調べます。

2つ目で、実際に見落としが1つ見つかりました。共通して使う部分は別ファイルに
切り出されて配信されるのですが、そこに Vite が足す先読みの補助コード（`fetch` を
使う）が入っていて、入口のファイルしか見ていなかった検査をすり抜けていました。
読みに行く先は自分のJavaScriptだけで本文は渡りませんが、**配信するものの中に
「外へ送れる道具」が1つも無い**状態のほうが確かめやすいので、その補助コードを
入れない設定にしました（`modulePreload: { polyfill: false }`）。動きは変わりません。

検査が本当に効くことは、次を仕込んで**すべてビルドが止まること**で確かめています。

| 仕込んだもの | 捕まえた検査 |
| --- | --- |
| `speech.ts` から声の判定を1か所消す | 読み上げの声 |
| 別の画面から直接 `speak()` する | 読み上げの声 |
| 共通コード（`src/lib`）に `fetch` を足す | 原文の通信の道具 |
| 隣のアプリ（製本所）に `sendBeacon` を足す | 同居アプリ |
| 語り部から、XHRを含む外部ライブラリを読み込む | 読み込みの筋をたどる検査 |
| ひとり版に1行差し込む | CSPのハッシュ（起動しない） |

### アプリでは守れない範囲

正直に書きます。**ここから先は、どんな作り方をしても残ります。**

- **スピーカーから出た音**は誰でも録音できます。ソフトウェアで防げるのは端末から先へ
  文字が渡ることまでで、聞こえている音そのものは守れません。人のいる場所では
  イヤホンをお使いください。
- **OSの読み上げエンジンそのもの。** `localService === true` は「ブラウザがそう
  申告している」ことであって、その先のOSの音声合成が何をするかはアプリからは
  見えません。Androidは読み上げエンジンを差し替えられるので、端末内で完結すると
  称するエンジンが実は通信していても、語り部には分かりません。
  **ブラウザの申告を信じる**、という前提の上に立っています。
- **ブラウザの拡張機能。** 拡張は独立した世界で動くので、`lockdown()` が塞ぐのは
  ページ側の道具だけです。拡張は自前の `fetch` で画面の文字を読んで送れますし、
  CSPも拡張には効きません。**拡張を入れていないブラウザか、ひとり版**が確実です。
- **OSのアクセシビリティ機能。** 画面の文字を取得できる仕組みは、Webアプリからは
  制御できません。
- **端末そのもの。** 画面の撮影・録画、端末を他人に使われること、別のアプリからの
  のぞき見は防げません。画面ロックの利用をおすすめします。
- **アプリ内ブラウザ。** LINEやメールのアプリの中で開いた画面は、そのアプリを通して
  表示されています。**ホーム画面に入れて**使うのが確実です。
- **元の `.md` ファイル自体。** クラウド保存の中にある原稿なら、そちらは語り部に
  入れる前からすでに同期されています。アプリの外側の話です。
- **配信元の記録。** 配信版を読み込むときだけは GitHub Pages に接続が残ります。
  そこに渡るのは「開いた」という事実だけで、本の中身も題名も渡りません。
  インストール後はオフラインで起動するため、その接続も起きなくなります。
  **ひとり版ならこれも起きません。**

## 文机（ふづくえ）

スマートフォンで書くことを主役にしたアプリです。

- **画面下のタブ**（執筆・資料・推敲・仕上げ）で、親指の届く範囲に主要な導線をまとめています。
- **和紙と墨**の配色。「端末に合わせる／紙（明るい）／墨（暗い）」から選べます。
- **縦書き（右から左）で執筆できます。** 市販の日本語の本と同じ流れで、書きながら
  仕上がりの見え方を確かめられます。ツールバーの切り替えボタンで横書きにもでき、
  選んだ状態は次回も引き継がれます。
- **執筆画面**は本文が主役。章の一覧・メモは下から出るシートで開き、
  集中モードにすると本文だけの全画面になります。
- **ルビ・傍点**は文字を選んでボタンを押すだけ。
- **挿絵を入れられます。** ツールバーの「画像」から選ぶと、長辺1600pxまでに縮めて
  端末内に保存し、**執筆画面のその位置に画像がそのまま表示されます**（縦書きなら
  文章のあいだに、横書きなら段落のあいだに入ります）。キャプションも付けられます。
  縦書きプレビューでは本の挿絵と同じように1枚で1ページを使い、EPUB・Wordには
  画像そのものが組み込まれます。
- **挿絵はアプリの中で修正できます。** 本文の画像を押すとそのまま修正画面が開きます。
  - **本文での大きさ**を「小・中・大・全面」から選べます。本文・縦書きプレビュー・
    EPUB・Wordのすべてに同じ大きさで反映されます。
  - **エフェクト**のひと押し切り替え（モノクロ・セピア・ふるい写真・あわい・くっきり・
    夕暮れ・夜あけ）。
  - **色の調整**：明るさ／コントラスト／あざやかさ／モノクロ／セピア／色あい／ぼかし。
  - **回転**（90度ずつ）・**左右反転**・**切り抜き**（枠をドラッグ、1:1などの比率も選べます）。
  - **別の画像への差し替え**。
  - **元の画像は残したまま「どう直したか」を保存する**ので、あとから切り抜き直したり、
    いつでも元の状態に戻したりできます。
- **表紙をつけられます。** 作品一覧で各作品の左端（背表紙の部分）を押すと画像を選べます。
  もう一度押すと修正画面が開き、切り抜き（KDP推奨の1:1.6の比率プリセットつき）や
  色の調整、差し替え、取り外しができます。つけた表紙はEPUB・Wordの表紙として
  書き出され、自動生成の表紙より優先されます。
- **推敲**は下記の校正エンジンをそのまま利用しています。
- **資料**に人物・筋書き・用語集をまとめられます。
- **仕上げ**で本の情報を整え、EPUB・DOCX・テキスト・バックアップを書き出せます。
  出す前の確認リストで、校正の「要修正」が残っていないかも確認できます。

### 挿絵の扱い

執筆画面は、本文を「文章のかたまり」と「挿絵」が交互に並んだものとして扱い、文章の部分だけを
`textarea` にしています。こうすると挿絵を実際の絵として見せながら、文字の入力・変換（IME）・
選択はブラウザ本来のものがそのまま使えます。挿絵のない章では `textarea` が1つだけになるので、
見た目も操作もこれまでとまったく同じです。

修正は「元の画像＋どう直したかの指示」として保存し、表示・書き出しに使う画像はそこから
作り直しています。元の画像を上書きしないので、切り抜きをやり直しても画質が落ちません。

画像そのものは本文には埋め込まず、端末内のデータベースに別に保存してIDで参照します。
こうすることで本文はあくまで軽いテキストのままなので、保存・校正・文字数カウントが
これまでどおり動きます（`［画像:ID］` の行は文字数にも校正の対象にも含めません）。
作品を削除すると、その作品の画像もあわせて削除されます。

表紙は挿絵とは別に保存しています（作品につき1枚）。書き出しのときは、表紙があれば
それを使い、なければ従来どおりタイトルから自動生成した表紙を使います。

**バックアップには挿絵と表紙も含まれます。** 「仕上げ」画面の「バックアップを保存」で作る
ファイルはZIPで、中身は次のようになっています。

```
work.json            作品（本文・人物・筋書きなど）
backup.json          画像の目録
images/<ID>.png|jpg  本文に表示している画像
originals/<ID>....   取り込んだままの画像（修正をやり直すため）
cover.png|jpg        表紙
```

挿絵のIDは本文の `［画像:ID］` が指しているので、読み込むときもIDはそのまま引き継ぎます。
別の端末で読み込めば、挿絵・表紙はもちろん、切り抜きや効果の設定、そして「元に戻す」ための
取り込んだままの画像まで、そのまま復元されます。作品のIDだけは、すでにある作品と衝突しない
よう振り直します。

以前の形式（本文だけのJSON）も、そのまま読み込めます。

## 小説執筆スタジオ（従来版）

### 主な機能

- **執筆**：作品ごとに章を分けて本文を執筆。自動保存、文字数カウント、目標達成率表示。スマートフォンなど
  画面が狭い環境では、本文欄を下から上にスワイプ（末尾までスクロールした状態からさらに上へ）すると
  全画面の執筆モードになり、上から下にスワイプ（先頭までスクロールした状態からさらに下へ）すると元に戻ります。
- **ルビ（振り仮名）・傍点**：執筆画面で文字を選んで「ルビ」「傍点」ボタンを押すと、本文に
  `｜漢字《かんじ》`・`《《強調》》` という記法（青空文庫・小説投稿サイトと同じ書き方）が入ります。
  漢字の直後に `《よみ》` と書けば親文字は自動判定されます。記号自体を書きたいときは `※《` のように
  `※` でエスケープできます。この記法は EPUB では `<ruby>`、DOCX では Word 標準のルビ（`w:ruby`／圏点）、
  印刷用PDFと縦書きリーダーではそれぞれの体裁に自動で組み替えられます。ルビの読みは本文の文字数には
  含めずに数えます。
- **推敲・校正（自動チェック）**：「推敲」画面で、出版原稿として整えておきたい点を端末内だけで
  自動チェックします（外部AIやサーバーは使いません）。
  - 検出できる項目：半角カタカナ、半角の！？、三点リーダー（`...`／奇数個の`…`）、ダッシュの統一、
    「！」「？」のあとの全角スペース、段落の字下げ、閉じ括弧の直前の句点、括弧の対応漏れ、
    句読点の重複、波ダッシュの統一、欧文引用符、段落末の句点漏れ、一文が長い、文末表現の連続、
    同語の繰り返し、重言、ら抜き言葉（地の文のみ）、助詞の重複、算用数字の漢数字化（任意）など。
  - 機械的に直せる指摘は**1件ずつ／まとめて自動修正**でき、直前の状態にいつでも**元に戻せます**
    （取り消し用のひかえは端末に保存されるため、画面を移動しても残ります）。
  - **表記ゆれ**（「できる／出来る」「サーバー／サーバ」など）を検出し、どちらに統一するかを
    ボタンひとつで一括置換できます。
  - **文体の傾向**を数値化した目安（会話文の比率・平均の文の長さ・漢字の比率・一文あたりの読点・
    文末表現のバリエーションなど）と、総合スコアを表示します。
  - チェック項目は個別にオン／オフでき、設定は端末に保存されます。
- **キャラクター管理**：登場人物のプロフィール・設定メモを一覧管理。
- **プロット管理**：あらすじと起承転結・シーン単位のプロットポイントを整理。
- **起承転結の自動下書き生成**：あらすじ・キャラクター設定・プロットポイントから、外部AIを一切使わず
  端末内だけで「起」「承」「転」「結」それぞれ約1,300字（4パート合計5,000字以上）の下書きを自動で組み立て、章として反映できます
  （テンプレート合成によるシンプルな下書きのため、そのままではなく必ず読み返して手直ししてください）。
- **章ごとの指示リライト**：執筆画面の「章をAIで修正」から、「情景描写を増やす」「心情描写を増やす」「会話を増やす」
  「緊迫感を高める」「もっと簡潔にする」という指示メニューを選ぶと、外部AIを使わず端末内のルールだけで本文を調整します
  （通信は発生しません）。必ずプレビューで内容を確認してから反映する仕組みで、反映後も1回だけ元に戻せます。
  起承転結のつなぎ文は「情感句＋述部」のように独立した部品を組み合わせる方式にしており、1パートあたり
  数千通りの組み合わせを生成できます。さらに一度使った組み合わせは端末内（IndexedDB）に記録して次回以降の
  作品では優先的に避けるため、同じ作品の中でも複数の作品をまたいでも言い回しが重複しにくくなっています
  （テンプレートの組み合わせという性質上、作品数が増えれば完全に重複をゼロにはできませんが、実用上ほとんど
  気にならない水準まで抑えています）。また、主人公キャラクターを登録していない場合でも、本文の主語が
  「主人公」という一般名詞のままにならないよう、作品ごとに決定的な人名を自動で割り当てます。
- **表紙・挿し絵の自動生成**：タイトル・ジャンルから、Canvas APIだけで水彩画風の表紙デザインと各章の
  装飾イラストを自動生成（実写や生成AIのイラストではなく、にじみと筆致による水彩表現）。EPUB・DOCX・
  印刷用PDFに自動挿入され、表紙はPNG単体でもダウンロードできます。
- **縦書きで書ける執筆画面**：執筆画面のツールバーの「縦書き」を押すと、原稿用紙が右から左へ流れる
  縦書きに切り替わります。市販の日本語の本と同じ流れのまま、そのまま入力・編集できます。選んだ状態は
  次に開いたときにも引き継がれ、「全画面」と組み合わせれば本文だけに集中できます。
- **縦書きリーダー**：文庫本のように縦書き・ページめくりで読めるプレビュー画面。スワイプ（左→右で次のページ）
  でページがめくれます。
- **出版準備**：書誌情報（タイトル・著者名・ジャンル・判型）の入力とKDP提出前チェックリスト（校正の
  「要修正」項目が残っていないかも自動で確認します）。
- **書き出し**：
  - EPUB（Kindle本アップロード用。自動生成した表紙・章ごとの挿し絵・目次を含む）
  - DOCX（Word。電子書籍・ペーパーバック双方に対応。表紙・挿し絵・目次ページ入り）
  - 印刷用PDFプレビュー（ペーパーバック判型に合わせたレイアウトをブラウザの印刷機能でPDF保存。表紙・目次・挿し絵入り）
  - TXT（プレーンテキスト。ルビ記法を残したまま出力すれば小説投稿サイトにそのまま貼り付けられます。本文だけの出力も選べます）
  - バックアップJSON（作品データ全体のエクスポート／インポート）
- **KDP出版ガイド**：KDPアカウント作成からアップロード、審査までの手順を日本語で解説。

## データの保存について

すべてのデータはブラウザの IndexedDB にのみ保存されます（サーバーには一切送信されません）。
4つのアプリは別々のデータベース（`fuzukue` / `shiori` / `seihonjo` / 既定ストア）を使うため、
作品や蔵書が混ざることはありません。製本所だけは既定で**何も保存しません**
（明示的に選んだときだけ保存します）。栞に取り込んだ本は、各本の保存ボタンから
いつでも元の `.md` として取り出せます。

ブラウザのデータを消去すると原稿も失われます。文机なら「仕上げ」画面、小説執筆スタジオなら
「出版準備」画面から、定期的に **バックアップ** を保存してください。別端末・別ブラウザ・
もう一方のアプリへ移すときは、保存したファイルを読み込めばそのまま続きを書けます
（文机は設定シート、小説執筆スタジオはダッシュボードから読み込めます）。

- 文机のバックアップは **ZIP** で、挿絵と表紙も一緒に包みます。
- 小説執筆スタジオのバックアップは従来どおり **JSON**（本文のみ）です。
- 文机は両方を読み分けるので、小説執筆スタジオのJSONもそのまま取り込めます。

同じ端末の同じブラウザであれば、ファイルを介さずに移せます。文机の「設定」に
「N件の作品を取り込む」というボタンが出るので、それを押してください。作品のIDはそのまま
引き継ぐので、二度押しても作品が増えることはなく、文机側で書き直した内容が上書きされる
こともありません。

なお、保存先はブラウザごとに分かれています。**アプリ内で開く簡易ブラウザ（SNSのリンクから
開いたときなど）は、ふだんのブラウザやインストールしたPWAとは別の保存先になります。**
書いたはずの作品が見あたらないときは、まず書いたときと同じブラウザで開いているかを
お確かめください。

## 開発

```bash
npm install
npm run dev      # 開発サーバーを起動
npm run build    # 本番ビルド（dist/ に出力）
npm run preview  # ビルド結果をローカルで確認
```

ビルド成果物は静的ファイルのみなので、GitHub Pages・Cloudflare Pages・Netlify
などの無料静的ホスティングにそのままデプロイできます（ルーティングは `HashRouter`
を、アセット参照は相対パス（`base: './'`）を使用しているため、リポジトリ名のサブパス
配下にデプロイしてもサーバー側のリライト設定は不要です）。

### 4つのアプリのビルド構成

`vite.config.ts` で4つのHTMLを入口に指定しています（`index.html`・`desk/index.html`・
`read/index.html`・`md/index.html`）。ビルドするとそれぞれが `dist/` 以下に出力され、
共通のロジックは1つのチャンクにまとめて共有されます。マニフェストとService Workerは
アプリごとに別ファイル（`public/`・`public/desk/`・`public/read/`・`public/md/`）を持ち、
それぞれが独立したPWAになります。

製本所のアイコンは `node scripts/make-md-icons.mjs` で作り直せます（画像ライブラリは使わず、
`public/md/favicon.svg` と同じ図形をその場でラスタライズしています）。

栞・製本所・語り部のHTMLには外部への通信を禁じるCSPを直接書き込んでいます。開発サーバーは
ホットリロードのためにインラインのスクリプトとWebSocketを使うので、
`vite.config.ts` の小さなプラグインが**開発中だけ**その2つを許した内容に差し替えます
（ビルド結果は元の厳しいままです）。

### GitHub Pagesへのデプロイ

`.github/workflows/deploy-pages.yml` が既定ブランチへのプッシュのたびに自動ビルド・
自動デプロイします。初回のみ、リポジトリの **Settings → Pages → Build and
deployment → Source** を `GitHub Actions` に設定してください。公開後のURLは
`https://<ユーザー名>.github.io/<リポジトリ名>/`（文机は `/desk/`、栞は `/read/`、製本所は `/md/`、語り部は `/voice/`）になります。

- idb-keyval（IndexedDBラッパー、ローカル永続化）

- Service Worker + Web App Manifest によるインストール可能PWA（アプリごとに別スコープ）
- CSS の縦書き（`writing-mode: vertical-rl`）と段組みによるページ組版（`src/read/paginate.ts`）
- 依存ライブラリを使わない自前の Markdown 解析（`src/read/markdown.ts`・`src/md/markdown.ts`）

外部APIやサーバーには依存しておらず、完全にクライアントサイドのみで完結します。
起承転結の下書き生成（`src/lib/draftGenerator.ts`）、校正・推敲（`src/lib/proofreader.ts`）、
ルビ・傍点記法の解析（`src/lib/inlineMarkup.ts`）、表紙・挿し絵の自動生成、栞の
Markdown解析とページ組版も、外部の生成AIサービスを一切呼び出さず、すべて端末内の
ロジックだけで完結しています。

### 栞のページ割りのしくみ

縦書きでは本文を `writing-mode: vertical-rl` で高さを固定して流し、右から左へ伸ばします。
そのうえで **1行ずつの位置を `Range.getClientRects()` で実測**し、ページ幅に収まる範囲で
区切っています。区切りは必ず行と行のあいだに来るので、字の大きさや画面比がどうであっても
**行がページの境目で割れることがありません**。

行の実測には、次の2つの工夫を入れています。

- **ルビは行の外側にはみ出して組まれる**ため、重なっている矩形どうしをひとかたまりに
  まとめてから区切り位置を決めます。まとめないと、区切りがルビの内側に来てしまいます。
- 傍点は要素ではなく文字の脇に描かれる装飾で矩形に表れないので、各行を
  **行送り1本ぶんの幅まで広げて**扱い、区切りが常に行の外側に来るようにしています。

さらに、本文を見せる窓（クリップ範囲）を**そのページの本文が終わる位置で閉じて**います。
窓を常にページ幅いっぱいに開けておくと、行の高さの端数のぶんだけ余白が生まれ、そこに
次のページの1行目が半分だけ覗いてしまうためです。

横書きではCSSの段組みに流し込み、1段を1ページとして扱います。段の分割はブラウザが
行単位で行うため、こちらは段の位置を数えるだけで済みます。どちらの場合も、各かたまり
（段落・見出し・挿絵）が何ページ目から始まるかを対応表にしているので、目次・検索・しおり・
読書位置の復元がすべて同じしくみで動きます。

これらは実機のChromiumで、5種類の画面サイズ × 縦横 × 3種類の字の大きさ（計30通り）に
ついて全ページを走査し、**窓に少しでも入っている行がすべて完全に収まっていること**を
確認しています。

### 校正エンジンの設計

指摘はすべて「本文中の位置（`index`）と長さ（`length`）」で表現し、自動修正できるものだけが
置換後の文字列（`replacement`）を持ちます。位置ベースに統一しているため、複数のルールの修正を
後ろの位置から順に適用するだけで、前方の位置をずらさずにまとめて反映できます。範囲が重なる指摘は
先に処理したほうを優先して読み飛ばします。

表記ゆれの集計と一括置換では、「サーバ」が「サーバー」の一部でもあるような部分文字列の関係を
扱う必要があります。数えるときは長い表記から順に伏せ字へ置き換えて二重に数えないようにし、
統一するときはいったんすべての候補を目印に置き換えてから統一先の表記に戻すことで、
「サーバーー」のような壊れ方を防いでいます。
